# KD360S / Primus Slim 1.0.13_HK

This is static analysis of a public OTA application image, not a dump of a
physical machine. All addresses below belong to this exact image. No hardware
capture, flash, modified firmware or live recorder has been validated here.

The filename and model path supply provenance; the pinned hash establishes byte
identity with the reviewed artifact. It is not a vendor signature or evidence
about secure boot / flash encryption on a physical chip.

Run from this repository with Python 3.9 or newer:

```bash
python3 scripts/kd360s_firmware.py fetch
python3 scripts/kd360s_firmware.py verify
python3 scripts/kd360s_firmware.py extract
```

The dedicated Slim tool keeps the upstream KD360X commands unchanged. It pins
one version rather than selecting a changing latest release. It verifies cache
and downloaded bytes before use, and checks ESP segment bounds, checksum and
appended digest before extraction. Outputs are ignored under `firmware_binary/`
and `analysis/extracted/kd360s/1.0.13_HK/`; the proprietary image is not shipped.
The tool uses normal HTTPS certificate validation regardless of stock behavior.

Public download bases, in order:

1. <https://wpmfirmwareprod.blob.core.windows.net/firmware/>
2. <https://wpm-firmware-updates-g9hfehacbzaphxfj.a01.azurefd.net/firmware/>

Append `KD360S/KD360S_OTA_1.0.13_HK_20260630.bin` for this image.
The stock manifest is `KD360S/KD360S_FW_lists.txt`. Both endpoints served identical
manifest and pinned image bytes during the 2026-10-10/11 investigation. A listed
historical version is not necessarily still downloadable.

## Stock network paths

| Path | Evidence / interpretation |
| --- | --- |
| Update UI | `4201e164` → `4201d334` → manifest `4201cca8` → parser `4201c808` |
| Manifest fallback | Primary first; fallback when HTTP status is not 200. No newer version after a 200 does not trigger fallback. |
| Version choice | Region HK initialized at `4201cf08`; numeric major/minor/patch comparison at `4201bd14`. |
| Binary download | `4201d280` → `4201cfb0`, using the successful manifest base. No separate binary fallback loop found. |
| TLS | Both manifest and binary paths reach `42100124` (`setInsecure`). Presence of a CA bundle alone does not prove certificate verification. |
| Request content | The two inspected OTA GET callers do not add MAC, serial or shot payloads. This is not a claim about every possible firmware path. |
| Leaving update | `4201bd80` disconnects station Wi-Fi. |
| Local DFU | AP callback `420145f0` → server setup `4200305c`, port 80. Routes `/`, `/update`, `/ota/start`, `/ota/upload` serve update functions. |

`GET /ota/start` changes update state and `POST /ota/upload` writes firmware;
neither is a read-only shot endpoint. HTTP/WebSocket/SSE library strings are not
proof of registered telemetry routes. No usable stock shot export interface was
found in the inspected application paths. Runtime coverage remains incomplete.

The updater's image checks and boot partition activation are distinct from TLS.
An unsigned public application image does not establish that a physical device
will boot a modified image.

## Actual data, targets and timing

| Source | Evidence / limitation |
| --- | --- |
| Pressure | GPIO19 ADC → filter `42004210` → calibration `42003da4`; actual sensor structure `0x3fc9d090 + 0x0c`. |
| Flow / volume | Internal UART parser `4200545c` writes sensor structure `+0x08` / `+0x10`; scaling and freshness need explicit decoder validation. |
| Control values | Structure `0x3fc9d0b8`: target pressure `+0x04`, actual pressure `+0x08`, target flow `+0x0c`, actual flow `+0x10`. |
| Debug change logs | `42005750` / `420057dc` report targets, not continuous actual sensor curves. |
| Shot lifecycle seeds | Start `42005918`; brew state machine `420088d8`; main loop `4200cc98`. End/abort transitions still need a complete table. |
| Internal UART | 19,200 baud, RX GPIO2 / TX GPIO1; parser recognizes header `0x67`, checksum/complement. Reply builder `420032ac` forms 37-byte control frames headed `0x76`. |
| Debug UART | 115,200 baud; no explicit debug command reader found in inspected application calls. Boot logs can expose stored Wi-Fi credentials. |

The serial callback `4200cc6c` timestamps first available data; the main loop
parses after more than 19 ms. This is not a demonstrated 20 ms idle delimiter.
Pressure is read through the ADC path; passive capture of the known UART fields
alone has not been shown to provide all shot measurements.

Timer API `403790d8` starts a nominal 25,000 microsecond period with callback
`4037546c`. Divider `42003ab8` produces 100 ms, 250 ms, 500 ms and 1 s flags.
The graph's counter and validity gate yield approximately one stored point per
second. A nominal 25 ms ADC/control tick is not proof that every sensor produces
40 fresh samples per second; boolean flags can coalesce and UART updates separately.

## Persistence

Loader `42006b70`, writer `420069d0` and history insert `42004b78` show:

| NVS key | Size | Meaning in this image |
| --- | --- | --- |
| `Settings/Record` | 95 bytes | Settings, not a shot archive |
| `UserData/CoffeeProfile` | 7,250 bytes | 50 storage slots of 145 bytes; not proof of 50 user-editable profiles |
| `UserData/HistoryProfile` | 1,450 bytes | 10 records of 145 bytes, shifted/overwritten when full |

The profile curve starts at record offset `0x16`, with at most 121 one-byte
points. VPS/VFS history follows pressure/flow targets, not a complete archive of
raw actual measurements. RAM curves reset for the next shot. The public OTA
image contains program code, not any owner's NVS or shot history.

Wi-Fi loads from `WifiData` (`SSID`, `Password`) at `4200605c`. Reset callback
`4201f124` calls `420040ac`, which clears credentials alongside other settings.
This is a machine reset, not a verified standalone Forget Wi-Fi operation.

## Evidence and repeatability

[Metadata and call tables](../analysis/kd360s/1.0.13_HK/) record the reviewed
snapshot. Ghidra 12.1.4 identified 6,375 functions and 30,352 call edges; 331
application bodies in `[0x42003000, 0x42024344)` were decompiled. Three application
call sites remained unresolved in the call graph: setup display virtual call
`4200c756`, and OTA stream calls `4201d1a9` / `4201d1bd`. A decompiler warning at
`420158e7` in `4201587c` also limits confidence. Counts are not coverage percentages.

The ported Ghidra helpers were executed during that investigation:

- `AuditSlim.java <image> <output-dir>` pins the hash, maps all segments in a fresh
  Xtensa little-endian 32-bit program, analyzes and exports selected references.
  It removes a seed memory block at address zero; use a disposable new project.
- `TraceSlim.java <output-file> <hex-address>...` follows literal references and
  decompiles owners in an already mapped program. Addresses omit the `0x` prefix.
- `InventorySlim.java <output-dir>` exports known functions/calls and application
  bodies from an already mapped and analyzed program.

For a fresh project, with `analyzeHeadless` on PATH:

```bash
mkdir -p ghidra_project ghidra_out/kd360s
analyzeHeadless ghidra_project SlimAudit \
  -import firmware_binary/kd360s/KD360S_OTA_1.0.13_HK_20260630.bin \
  -loader BinaryLoader -loader-baseAddr 0 -processor Xtensa:LE:32:default \
  -scriptPath ghidra_scripts \
  -postScript AuditSlim.java \
    firmware_binary/kd360s/KD360S_OTA_1.0.13_HK_20260630.bin ghidra_out/kd360s
analyzeHeadless ghidra_project SlimAudit \
  -process KD360S_OTA_1.0.13_HK_20260630.bin -noanalysis \
  -scriptPath ghidra_scripts \
  -postScript TraceSlim.java ghidra_out/kd360s/data-path.txt \
    4200545c 42004210 42003da4 42005918 420088d8
```

Do not repeat the import/mapping step on an already mapped project. These helpers require
Ghidra's Xtensa language support and Java 21 for the tested environment. They are
not integrated into the upstream `run_ghidra.sh`, which has KD360X paths/addresses.
Save projects under `ghidra_project/` and generated dumps under `ghidra_out/`.
Do not publish raw proprietary decompilation or real device credential logs.

## Tooling validation (2026-10-11)

The 16 synthetic-image tests passed on Python 3.9.6 and 3.12.14. The integrated
CLI downloaded the pinned public artifact, verified it, extracted all five
segments, and reused its verified cache. Independent byte comparisons matched
all extracted payloads to the original image. Repeated extraction was idempotent;
a one-byte-corrupted copy was rejected by the CLI without a traceback. The
[resulting segment metadata](../analysis/kd360s/1.0.13_HK/image-segments.json)
records addresses, offsets and hashes; downloaded binaries and extracted payloads
were removed after validation. Ghidra helpers were ported unchanged from the
previous investigation and were not rerun during this tooling check.
